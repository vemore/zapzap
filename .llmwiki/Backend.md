## Facts

### Crate
- Package `zapzap-backend` 0.1.0, edition 2021 (`zapzap-rust/Cargo.toml:2`). The library `lib.rs` declares the four modules (`zapzap-rust/src/lib.rs:4-7`); the binary `main.rs` declares none and links the library (`zapzap_backend::api::build_app`), the router the tests drive too. ### AppState (`zapzap-rust/src/infrastructure/app_state.rs`)
- Fields: `db: SqlitePool`, `jwt_service`, `session_manager`, `user_repo`, `party_repo`, `event_sender`/`event_receiver` (async-broadcast), `llm_service: Option<Arc<dyn LlmService>>`, `llm_memories` (per-bot `LlmBotMemory` map), `bot_strategies_dir` (where they are saved), `bot_runner` (per-party bot loops and strategies, see Bot triggering), `google_oauth: Option<Arc<GoogleOAuthService>>`. The fields are public: a test changes them before wrapping the state in its `Arc` (`test_app_with`, `zapzap-rust/tests/rules_and_bots_tests.rs`).
- DB: `SqlitePool::connect(&db_url)` (`:100`) — no `create_if_missing`, so the file must already exist (it may be empty: the tables are created, see below).
- LLM priority Bedrock > Ollama > None; the startup probe runs before the port is bound, so it is bounded: `probe_within(what, STARTUP_PROBE_TIMEOUT, service)` (10 s, `llm_service.rs`; called from `AppState::new`, switches read by `llm_enabled`) keeps a service whose `health_check()` answers true, drops one that answers false, and keeps unverified, with a warning, one that has not answered at 10 s (a cold model): its first real call decides, and a failed call makes the bot play its fallback. The Bedrock client creation has its own 10 s bound (a timeout drops Bedrock). The Bedrock health check is cheap: user prompt `OK`, `max_gen_len` 5 (`HEALTH_CHECK_*`, `bedrock_payload`). With no LLM, LLM bots use a fallback strategy (see [[Bots]]).
- `get_llm_memory` lazily creates and `load()`s a bot's memory (`:187-205`).

### Database schema situation
- **The Rust backend creates its schema at startup**: `AppState::new()` reads `JWT_SECRET`, connects, then calls `schema::ensure_schema(&db)` (`zapzap-rust/src/infrastructure/app_state.rs`, `AppState::new`), which runs `zapzap-rust/src/infrastructure/database/schema.sql` through `sqlx::raw_sql` **in one transaction** (`schema.rs`): a failing statement rolls back the ones before it and leaves the database as it was.
- A `users` table rebuilt by `scripts/docker-entrypoint.js` (its `users_new` has no `google_id`/`email`) and not yet opened by the Node app makes that step fail on `CREATE INDEX idx_users_google_id` ("no such column"), so the backend refuses to start, with the database untouched (`schema_step_failure_leaves_the_database_unchanged`). The Node `ADD COLUMN` steps are not ported: at the switch, the Node app must have opened the database once ([[Deployment]]).
- `schema.sql` is the Node DDL verbatim: the `createSchema()` string of `src/infrastructure/database/sqlite/DatabaseConnection.js:69-240` (users, parties, party_players, rounds, game_state, round_scores, game_results, player_game_results, game_actions, 19 indexes) plus the two users indexes of its `runMigrations()` (`idx_users_google_id`, `idx_users_email`). Every statement is `IF NOT EXISTS`, so on a database the Node backend built it changes nothing.
- No sqlx migrations and no `_sqlx_migrations` table: the production DB has none, and `sqlx::migrate!` would start managing it. The Node `ALTER TABLE ... ADD COLUMN` steps and the password_hash table rebuild are not ported — they upgrade databases created by older Node versions, and every database the current Node code has opened (production's included) already went through them.
- `zapzap-rust/tests/schema_tests.rs` holds both halves: `rust_schema_matches_node_schema` builds a DB the way a fresh Node one is built — the `createSchema()` DDL, then `runMigrations()`'s `ALTER TABLE ... ADD COLUMN` statements (a duplicate column ignored, as Node does) and `CREATE INDEX` calls, all read from the `.js` file at compile time — and one from `schema.sql` and compares `sqlite_master` statement for statement; `schema_step_is_a_noop_on_a_node_built_database` fills a Node-built file DB (with the extra `idx_users_username`/`idx_users_user_type` of `scripts/docker-entrypoint.js`), runs `AppState::new()` and `ensure_schema` again, and checks that schema and rows are unchanged. A Node schema change without the same change in `schema.sql` turns it red.
- The older `src/infrastructure/database/schemas/schema.sql` (subset + `schema_version`) is loaded only by the legacy `src/infrastructure/database/sqlite/connection.js:78`, not by `DatabaseConnection.js`.
- Rust writes: parties/party_players/rounds/game_state/game_actions/round_scores/game_results/player_game_results in `zapzap-rust/src/infrastructure/database/repositories/party_repo.rs:253-730`; users upsert in `user_repo.rs:136` (includes `google_id`, `email` columns).

### Auth
- JWT HS256 (`Header::default()`), claims `userId`, `username`, `isAdmin` (default false), `exp`, `iat` (`zapzap-rust/src/infrastructure/auth/jwt_service.rs:7-15`). Lifetime `7 * 24 * 60 * 60` s = 7 days (`:28`). `decode_without_verify` exists, unused (`:60`).
- Google OAuth (`zapzap-rust/src/infrastructure/services/google_oauth.rs`): `verify_id_token` (`:168`) requires an RS256 token whose `kid` is in Google's JWKS (`https://www.googleapis.com/oauth2/v3/certs`, `:16`), `aud` = `GOOGLE_OAUTH_CLIENT_ID`, `iss` `accounts.google.com` or `https://accounts.google.com`, a valid `exp` (jsonwebtoken default 60 s leeway), and `email_verified` true. Keys are cached 1 h (`:22`). Stale keys or an unknown `kid` trigger a refetch, under one mutex (concurrent requests wait for a single fetch) and at most one attempt a minute, failed or not (`:25`); a failed refetch keeps the stale keys, and its error text is logged, never answered. The JWKS is parsed key by key, skipping keys of an unknown `kty`/`alg` (`parse_jwks`). The client id is trimmed. Tests inject a key set (`GoogleOAuthService::with_keys`) or a fetcher (`with_fetcher`) and never reach the network. A first login that loses a race with a concurrent one (username UNIQUE violation on save) answers the winner's user, found again by `google_id`; `users.google_id` has no unique index (Node's DDL), so this relies on both requests picking the same username. Username of a new Google user: Node's `generateUsername`/`generateUniqueUsername` (`generate_username`, `username_candidate`).
- `auth_middleware` requires `Authorization: Bearer <token>` whose user **still exists** in the database (one primary-key lookup, `user_exists`; Node: `src/use-cases/auth/ValidateToken.js`), else 401 with Node's body and code (`MISSING_AUTH_HEADER`, `INVALID_AUTH_FORMAT`, `INVALID_TOKEN`, [[Api]]; `zapzap-rust/src/api/middleware/auth_middleware.rs`, which reads the header with `bearer_token`, shared with the optional middleware). `optional_auth_middleware` attaches claims under the same two conditions (a malformed header or a bad token goes on without claims, as Node's optional middleware). `admin_middleware` is mounted on every `/api/admin` path, unknown ones included (the router's fallbacks are wrapped too), and on `POST /api/bots` / `DELETE /api/bots/:botId`, inside `auth_middleware` (`create_admin_router`, `zapzap-rust/src/api/routes/mod.rs`): it reads `is_admin` **from the database**, as Node's `adminMiddleware.js` does, and answers 401 `AUTH_REQUIRED` / 403 `ADMIN_REQUIRED` with `{success:false, error, code}`. It is the only admin check (the handlers in `admin.rs` no longer read `claims.is_admin`, as in Node): a promotion or a revocation takes effect at once, whatever the token says.
- Party membership: the game use cases check the caller themselves; `nextRound` and `trigger-bot` check it in the handler through `require_party_member` (`zapzap-rust/src/api/access.rs`: 404 `PARTY_NOT_FOUND`, 403 `NOT_IN_PARTY`). Private parties: join needs the invite code, details and history are for members only ([[Api]]).
- Passwords: new hashes are bcrypt at Node's cost 10, `$2b$10$...` (`BCRYPT_COST`, `zapzap-rust/src/infrastructure/auth/password.rs:7-20`), which Node's `bcryptjs.compare` verifies; `verify` dispatches on prefix `$argon2` vs `$2` (bcrypt: Node's `$2a$`/`$2b$` and Rust's), anything else → `UnknownFormat` (`:38-48`). Login never rewrites the stored hash, and a stored hash `verify` cannot read (unknown format, truncated bcrypt) is logged and answered 401 `INVALID_CREDENTIALS`, as Node's `bcrypt.compare` answers false for it (`zapzap-rust/src/application/auth/login_user.rs`). The cross-check: `zapzap-rust/tests/fixtures/bcrypt_node_compat.json` holds a hash Rust wrote and one bcryptjs wrote, verified by the Rust tests in `password.rs` and by the jest test `tests/unit/infrastructure/auth/RustBcryptCompat.test.js`.

### Event broadcaster / SSE
- `broadcast(1000)` with `set_overflow(true)`: when full, oldest events are dropped instead of blocking (`app_state.rs:114-115`). `broadcast_event` uses `try_broadcast` and only logs errors (`:208-226`).
- `GameEvent` JSON: `type`, `partyId`, `userId`, optional `action`, flattened `data`, `timestamp` ms (`app_state.rs:230-244`). Event types emitted: `partyUpdate` (actions `partyCreated`, `playerJoined` — also when the owner adds a bot, with the bot as `userId` —, `playerLeft`, `partyStarted`, `partyDeleted` — with the `visibility` the deleted party had), `gameUpdate` (`selectHandSize`, `play`, `draw`, `zapzap`, `roundStarted`, `gameFinished`), `userConnected`, `userDisconnected`.
- `GET /suscribeupdate?token=<jwt>` (`zapzap-rust/src/api/sse.rs`): token optional, passed in the query string. Sends an initial `connected` event, then each GameEvent as SSE event `event`, a `heartbeat` comment every 20 s, plus axum's default keep-alive comment; response header `X-Accel-Buffering: no` (and axum's `Cache-Control: no-cache`) so no proxy buffers the stream.
- **Per-user filtering** (`should_deliver`, `sse.rs`): an event without `partyId` (`userConnected`, `userDisconnected`, `userStatusChanged`) goes to every stream, as Node sends everything to everyone; so does a **public** party's lifecycle event (`PUBLIC_LIFECYCLE_ACTIONS`: `partyCreated` (emitted for public parties only), `playerJoined`, `playerLeft`, `partyStarted`, `partyDeleted`, `gameFinished` — names, indexes and ids only), which the Flutter `PartyListProvider` reloads the party list on; a `partyDeleted` carries the `visibility` the deleted party had. Every other party event — `gameUpdate` moves, and every event of a **private** party — goes only to a stream whose token names a player of that party (checked in `party_players` per event), or whose own action it reports (the player who just left), and a `partyDeleted` also to the streams that were players of it when they opened or since (its membership rows are gone by then). If the membership lookup fails, the stream goes by the parties it already knew and changes nothing. A token whose user no longer exists names nobody. A stream without a valid token gets the events that go to everyone only. Node filters nothing (`src/api/server.js:69-151`).
- On a receiver error (e.g. lagging) the stream breaks and the client must reconnect.
- An authenticated stream owns a `StreamGuard` (`sse.rs`): when the client goes away axum drops the stream, and the guard's `Drop` unregisters it from the session manager; the user's last stream broadcasts `userDisconnected` (with `username`), their first one `userConnected`, as Node (`src/api/server.js`). Tests: `test_sse_disconnect_unlists_the_user_after_the_last_stream` (`zapzap-rust/tests/api_tests.rs`).

### Session manager
- In-memory, lost on restart (`zapzap-rust/src/infrastructure/services/session_manager.rs`): the sessions by user id, and the number of open event streams per user, as Node's `SessionManager.streams`. `connect` registers a stream and returns the new session (status `lobby`) only on the user's first one; `disconnect` unregisters one and returns the removed session only on the last one. Two tabs, or a reconnection whose new stream opens before the old one closes, keep the user listed with their session as it was.
- `update_status` is never called, so every session stays `lobby` with `partyId: null`.
- `GET /api/players/connected` returns at most 5 sessions, newest first (`zapzap-rust/src/api/routes/players.rs:39`).

### Bot triggering
- No bot scheduler: bots move when a request triggers them. `GET state` (100 ms delay), `selectHandSize`, `play`, `draw` and `nextRound` (300 ms) call `spawn_bot_turns` (`zapzap-rust/src/application/bot/runner.rs`), which runs `trigger_bot_turns` in a `tokio::spawn`. The loop plays while the current player is a bot, pausing after each action for `BOT_ACTION_DELAY_MS` (`BotRunner::action_delay`, 1000 ms by default as Node; the tests run at 200 ms; `test_bot_actions_pause_for_bot_action_delay_ms`).
- **One loop at a time per party**: `AppState.bot_runner` (`BotRunner`) keeps one slot per party — a `pending` flag and the party's `Roster` behind a tokio mutex. A trigger sets `pending` and returns at once when a loop holds the mutex; the running loop goes round again while `pending` is set, and re-checks it after unlocking, so no trigger is lost and no two loops act on the same party. The slot is dropped when the party is no longer playing, and at once when the party is deleted (`BotRunner::drop_party`, from `DELETE /api/party/:id` and the admin delete); a loop that runs meanwhile finds no game state at its next action and ends.
- **One strategy per bot for the game**: the `Roster` builds a bot's `BotBrain` (a rule-based `BotStrategy`, or the `LlmBotStrategy`) on its first move and hands back the same instance afterwards; hand size is the strategy's choice, clamped by `hand_size_bounds` (`game_service.rs`: 4-7, 4-10 in Golden Score, at most (54 − 1) / active players). See [[Bots]].
- Action cap per loop: 50 if an active human remains, 500 if only bots (`MAX_ACTIONS_WITH_HUMANS`, `MAX_ACTIONS_BOTS_ONLY`).
- Manual `POST /api/game/:partyId/trigger-bot` (`game.rs`) calls `run_bot_turns_now`, which waits for the party's running loop, then runs one itself and answers the number of actions taken (500 `BOT_ACTION_ERROR` on a failed bot action). A trigger that came meanwhile is served afterwards in the background (`serve_pending`; test `test_trigger_during_a_manual_loop_is_served_after_it`).
- After a ZapZap (a human's, from `game.rs`, or a bot's, from the loop), `trigger_llm_reflection` (`runner.rs`) runs `ReflectOnRound` for each LLM bot if an LLM service exists, with the round outcome `round_outcome` reads from the round-end state: `score_change` is the points the round added to the bot's total (`round_scores`).
- Pending bot turns are not recovered at startup (the Node `BotOrchestrator.recoverPendingBotTurns`, `src/infrastructure/bot/BotOrchestrator.js:59`, has no Rust equivalent); the next `GET state` restarts them.

### Error mapping
- The party and game handlers return `Result<_, ApiError>` (`zapzap-rust/src/api/error.rs`): one `From<UseCaseError> for ApiError` per use case maps each variant to Node's status and `code`; no handler reads an error's message. A repository failure is a 500 in Node's shape (`{error: "Failed to …", code: "<ROUTE>_ERROR", details}`), logged by `IntoResponse`.
- JSON bodies go through `ApiJson<T>`: a body that does not parse (malformed JSON, a missing or mistyped field) answers 400 `{error, code}` (Node's body: no parser message in `details`, which the parity suite compares) with the code the route gives a missing field (`ApiBody::INVALID_CODE`), never axum's 422 plain text; a request without a JSON content type reads as `{}`, as Express does.
- The auth, admin, bots, stats and history handlers still build their errors inline (no message matching there).

## Decisions & History
- 2026-09-25 (fix/rust-keeps-bcrypt): the Rust backend keeps passwords in bcrypt while the Node backend is the rollback of the production switch (user decision, 2026-09-24). It used to hash new passwords with Argon2 and rehash a bcrypt hash to Argon2 on every password login; Node's `bcryptjs.compare` answers `false` for Argon2, so a rollback locked out every password user who had logged in or registered on Rust (reproduced in a rehearsal: 401 `INVALID_CREDENTIALS`). Registration now hashes with bcrypt at Node's cost and login leaves the hash alone; Argon2 hashes still verify. Argon2, with a rehash on login, can come back once Node is no longer the rollback. The same change bounded the LLM startup probe to 10 s: `BedrockService::new` and its health check ran unbounded before the port was bound, so an unreachable Bedrock endpoint could hold up the boot. After review: production sets `AWS_BEDROCK_ENABLED=true` and the health check asked for 512 tokens, so a cold model could miss the cap and disable LLM bots until a restart; the check now asks for 5 tokens and a timed-out probe keeps the service unverified rather than dropping it (a background re-probe was the alternative, more moving parts for the same outcome). A malformed stored hash answered 500 `LOGIN_ERROR`; it answers 401 like Node.
- 2026-09-24 (fix/rust-before-switch), the last gaps before production switches to Rust: the SSE disconnect cleanup sat after the stream's loop, which only a broadcast error ends, so a client going away never left `GET /api/players/connected`; it moved into a guard's `Drop`, with streams counted per user as Node does (a second tab closing no longer unlists the first). Bot turns pause for `BOT_ACTION_DELAY_MS` (production sets 2000) rather than a fixed 200 ms. `main.rs` links the library crate instead of compiling the modules a second time, now that the image build removes the dummy crate's fingerprints. An unwritable `BOT_STRATEGIES_DIR` (root-owned on the NAS, the image runs as uid 1000) is a warning, never a failed bot turn.
- 2026-09-24 (fix/rust-rules-and-bots): bot turns moved out of `api/routes/game.rs` into `application/bot/runner.rs`, behind a per-party lock with a `pending` flag — concurrent polls used to start one loop each, which read the same state and played the same bot turn twice (a test replaying six polls and six triggers at once saw six plays for one turn). Strategies are kept per bot for the game, because Thibot's play/draw coordination and VinceBot's round memory were rebuilt away on every action. The image gained the `CARGO_FEATURES` build arg and the compose file the LLM variables; a present LLM switch (`AWS_BEDROCK_ENABLED`, `ENABLE_LLM_BOTS`) now decides alone, `false`/`0`/empty meaning off, since the Node compose file sets `AWS_BEDROCK_ENABLED=false` next to real AWS keys. After review: `run_bot_turns_now` serves a trigger that came during the manual loop (it used to be lost when the loop ended on a human's turn), and hand sizes are bounded by the deck (`hand_size_bounds`).
