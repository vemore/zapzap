## Facts

### Startup (`zapzap-rust/src/main.rs`)
- Arguments: none serves the API; `seed` and `seed --demo` seed the accounts and exit (§ Seeding); anything else prints the usage and exits 1. The steps below are the server's (`serve`).
- First `health::start_clock()`, the start of the uptime `/api/health` reports (`:23`). `dotenvy::dotenv()` loads `.env` (`:26`). Tracing filter from `RUST_LOG`, default `zapzap_backend=debug,tower_http=debug` (`:31-32`).
- Router: `api::build_app` (`zapzap-rust/src/api/mod.rs`): `/api` nested from `create_api_router`, `/suscribeupdate` SSE, `/health`, then `route_not_found` (Node's 404 body) as the fallback of unknown paths and, through `method_not_allowed_fallback`, of unserved methods (the `/api` router sets its own unknown-path fallback, the `/api/admin` router both, behind its auth and admin layers), the CORS layer of `AllowedOrigins::layer` (`zapzap-rust/src/infrastructure/cors.rs`: the origins of `ALLOWED_ORIGINS`, below), `TraceLayer`. No timeout layer although `tower-http` `timeout` feature is enabled.
- Before the router, `serve` spawns the turn timer (`spawn_turn_timer(state, TURN_TIMER_TICK)`, § Turn timer).
- Binds `0.0.0.0:$PORT`, default 9999 (`:45-50`).

### AppState (`zapzap-rust/src/infrastructure/app_state.rs`)
- Fields: `db: SqlitePool`, `jwt_service`, `session_manager`, `user_repo`, `party_repo`, `event_sender`/`event_receiver` (async-broadcast), `llm_service: Option<Arc<dyn LlmService>>`, `llm_memories` (per-bot `LlmBotMemory` map), `bot_strategies_dir` (where they are saved), `bot_runner` (per-party bot loops and strategies, see Bot triggering), `google_oauth: Option<Arc<GoogleOAuthService>>`, `clock: Arc<dyn Clock>` (`SystemClock`; the time of the turn clock, § Turn timer), `guest_limiter: Arc<RateLimiter>` (§ Guest accounts; a test swaps in its own limits) and `trusted_proxy_hops`. - DB: `SqlitePool::connect(&db_url)` (`:94`) — no `create_if_missing`, so the file must already exist (it may be empty: the tables are created, see below); `zapzap-backend seed` creates it (§ Seeding).
- LLM priority Bedrock > Ollama > None; the startup probe runs before the port is bound, so it is bounded: `probe_within(what, STARTUP_PROBE_TIMEOUT, service)` (10 s, `llm_service.rs`; called from `AppState::new`, switches read by `llm_enabled`) keeps a service whose `health_check()` answers true, drops one that answers false, and keeps unverified, with a warning, one that has not answered at 10 s (a cold model): its first real call decides, and a failed call makes the bot play its fallback. The Bedrock client creation has its own 10 s bound (a timeout drops Bedrock). The Bedrock health check is cheap: user prompt `OK`, `max_gen_len` 5 (`HEALTH_CHECK_*`, `bedrock_payload`). With no LLM, LLM bots use a fallback strategy (see [[Bots]]).
- `get_llm_memory` lazily creates and `load()`s a bot's memory (`:187-205`).

### Password reset (`zapzap-backend reset-password <username>`)
- `zapzap-rust/src/infrastructure/database/reset_password.rs`, run by `main.rs`'s `run_reset_password`: reads the new password from **one line of stdin, never argv** (so it never lands in a shell history or a process list), bcrypt-hashes it through `PasswordService::hash` (Node's cost 10, as registration hashes) and overwrites the user's `password_hash` through `UserRepository::find_by_username` + `save` (the trait's upsert). `NotFound` when no such username exists, the database untouched; the CLI then exits 1 with `no such user: <username>` (an empty line on stdin exits 1 too, `empty password on stdin`, before opening the database). It needs no `JWT_SECRET`, opens the database `database_url()` names the same way `seed::open` does (creating the file if missing), and does not revoke the account's other JWTs (issued before the reset, still valid until they expire — no password version in the claims).
- Where: `cargo run -- reset-password <username>` (piped stdin) in `zapzap-rust/`; in production `docker compose exec -T backend /app/zapzap-backend reset-password <username>` (`-T`: no pseudo-tty, so the piped password reaches the binary; `.claude/skills/deploy/SKILL.md` § Reset a user's password). Replaces the Node backend's `reset-password.js` script, removed with it (it hard-coded one username/password pair). Tests: `test_reset_password_logs_in_with_the_new_password_and_the_old_one_answers_401`, `test_reset_password_of_an_unknown_username_answers_not_found` (`zapzap-rust/tests/api_tests.rs`).

### Database schema situation
- **The Rust backend creates its schema at startup**: `AppState::new()` reads `JWT_SECRET`, connects, then calls `schema::ensure_schema(&db)` (`zapzap-rust/src/infrastructure/app_state.rs`, `AppState::new`), which runs `zapzap-rust/src/infrastructure/database/schema.sql` through `sqlx::raw_sql`, then the migrations the database has not had (`MIGRATIONS`, below), **in one transaction** (`schema.rs`): a failing statement rolls back the ones before it, `user_version` included, and leaves the database as it was.
- A `users` table rebuilt by the Node image's entrypoint (its `users_new` has no `google_id`/`email`) and never opened by the Node app since makes that step fail on `CREATE INDEX idx_users_google_id` ("no such column"), so the backend refuses to start, with the database untouched (`schema_step_failure_leaves_the_database_unchanged`). The Node `ADD COLUMN` steps are not ported, and nothing runs them any more: production's database had gone through them before the switch ([[Deployment]]).
- **`schema.sql` and `MIGRATIONS` are the one source of truth for the schema.** `schema.sql` is the Node DDL verbatim — the `createSchema()` string of the Node backend's `DatabaseConnection.js` (users, parties, party_players, rounds, game_state, round_scores, game_results, player_game_results, game_actions, 19 indexes) plus the two users indexes of its `runMigrations()` (`idx_users_google_id`, `idx_users_email`) — so production's database, which Node built, already has it. Every statement is `IF NOT EXISTS`, so on that database it changes nothing; it is never edited, a change is a migration.
- **Migrations**: `MIGRATIONS` (`schema.rs`), SQL steps run in order after the DDL, counted in `PRAGMA user_version` (the step at index `n` takes it from `n` to `n + 1`). The Node backend never set `user_version`, so its database is at 0 and a fresh one runs the DDL then every step: both end with the same schema. A database a newer binary migrated further is left alone. Step 1: `ALTER TABLE game_state ADD COLUMN version INTEGER NOT NULL DEFAULT 0` (§ Game-state writes). Step 2: `CREATE UNIQUE INDEX IF NOT EXISTS idx_users_google_id_unique ON users(google_id) WHERE google_id IS NOT NULL` — one user per Google account, any number of users without one (§ Google OAuth); Node's plain `idx_users_google_id` stays. A database holding two users of one `google_id` fails it, and the server refuses to start with the file unchanged (`google_id_migration_refuses_duplicates_and_leaves_the_database_unchanged`). Step 3: `ALTER TABLE users ADD COLUMN is_guest INTEGER NOT NULL DEFAULT 0` (§ Guest accounts; existing users 0). The steps are additive, so an older image rolled back to reads and writes the migrated file as before (it ignores `is_guest`; its `save` upsert names its columns, so it leaves the column alone).
- No sqlx migrations and no `_sqlx_migrations` table: the production DB has none, and `sqlx::migrate!` would start managing it; `user_version` counts the migrations instead. The Node `ALTER TABLE ... ADD COLUMN` steps and the password_hash table rebuild are not ported — they upgraded databases created by older Node versions, and production's had already gone through them.
- `zapzap-rust/tests/schema_tests.rs` checks it against a frozen fixture, `zapzap-rust/tests/fixtures/node_built_schema.sql`: the `sqlite_master` of a database the Node backend built (`createSchema()`, `runMigrations()`, then the `idx_users_username`/`idx_users_user_type` of the Node image's entrypoint), generated once from commit `1640580` (the recipe heads the file) — nothing outside `zapzap-rust/` is read. `rust_schema_matches_the_node_built_schema_and_its_migrations` compares a fresh DB with it statement for statement (the two entrypoint indexes aside, `game_state` with its migrated `version`), then upgrades the fixture DB and checks it ends where the fresh one starts; `schema_step_upgrades_a_node_built_database_and_keeps_every_row` fills a DB built from it, runs `AppState::new()` and `ensure_schema` again, and checks that the first run changed only what the migrations change (every row kept, `game_state` rows at version 0) and the second nothing, and that the upgraded DB refuses a second user of an existing `google_id`; `users_google_id_is_unique_when_set_and_null_repeats` saves through `SqliteUserRepository`. Migration 3 is checked the same way: `users` ends with its `is_guest` column in both, and the upgraded rows read 0 (`schema_step_upgrades_a_node_built_database_and_keeps_every_row`). The fixture stands for a database that exists and is not edited to follow `schema.sql`: a schema change is a migration that must pass against it.
- Rust writes: parties/party_players/rounds/game_state/game_actions/round_scores/game_results/player_game_results in `zapzap-rust/src/infrastructure/database/repositories/party_repo.rs:253-730`; users upsert `save` in `user_repo.rs` (every column, `google_id`, `email` and `is_guest` included).

### Game-state writes (optimistic locking)
- A party's game state is one `game_state` row (`state_json`) with a `version`, bumped by every write. A use case reads it with `get_versioned_game_state` and writes it back through the compare-and-swap: one `UPDATE … SET version = version + 1 WHERE party_id = ? AND version = ? AND` the party is `playing`, and zero rows written is `RepositoryError::Conflict`, with nothing written (`party_repo.rs`). A state deleted meanwhile (the party gone) is `NotFound` instead, answered 404 `PARTY_NOT_FOUND`.
- Every game use case — `select_hand_size`, `play_cards`, `draw_card`, `call_zapzap`, `next_round` (`zapzap-rust/src/application/game/`) — writes through **`write_game(GameWrite)`**: one `BEGIN IMMEDIATE` transaction whose first statement is the compare-and-swap, then what the use case changed and nothing else: the round row of the state's `round_number` (`RoundWrite`: `Progress` its turn and action, `Finish` it with its `round_scores`, `Start` a new row and `parties.current_round_id`), and at the game's end (`winner`) `parties.status` and the results (`write_game_results`, below). So a conflict writes nothing at all, a failure after the compare-and-swap (a round row refused) rolls the state back with it, and a party field written by someone else since the use case read the party (a forfeit's new owner) stands: only the fields the use case changes are written, never the whole row. A second `nextRound` at once is a conflict rather than a 500 on `UNIQUE(party_id, round_number)`. The round row is the state's round, not the `parties.current_round_id` read before the transaction, so a move cannot write into the round a concurrent `nextRound` began.
- `write_game_results(conn, party, state, winner)` (`party_repo.rs`) reads the seats, the recorded eliminations and the players the turn timer ejected on the transaction's connection, builds the ranking (`build_game_results`, [[GameRules]] § Final ranking) and upserts `game_results` and `player_game_results`; no caller passes it the ejected players. An ejected player's account deleted as the game ends (`delete_account`, also `BEGIN IMMEDIATE`) is serialised on SQLite's write lock: before, their row is read and rewritten under its anonymous `deleted-` id; after, it is renamed with the rest. It cannot land between the read and the write, where the upsert on the deleted id used to fail the foreign key (500 after the party was finished).
- `save_game_state` writes whatever is stored (an upsert, still a new version): a game's first state (`start_party`) and the tests' setups. The forfeit of an account deletion (`forfeit_playing_seats`, `user_repo.rs`) reads and writes under its `BEGIN IMMEDIATE` lock and bumps the version, so a move that read before it is refused. The admin stop (`stop_party`, `admin.rs`) finishes the party and bumps the version in one transaction: a move that read the state before the stop is refused by the version, one that read the party before it (still `playing`) and the state after it by the status the compare-and-swap checks.
- The compare-and-swap is one function, `write_game_state_if_unchanged` (`party_repo.rs`), on a connection: `update_game_state` runs it on the pool for a write of the state alone (the bot loop's hand-over past an eliminated bot, the startup deadline extension), `write_game` and the turn timer's `replace_player` inside their transactions (§ Turn timer). A player's move (`select_hand_size`, `play_cards`, `draw_card`, `call_zapzap`, bots included) passes `GameWrite::seat_holder`, and the `UPDATE` then also requires, in the same statement, that `party_players` still gives the seat to that user: a move that checked its seat before an ejection and read the state after it (seat and version change in one transaction, the turn does not) is a `Conflict` (409), not a move on the bot's seat. Every write — the compare-and-swap, `save_game_state` and the forfeit — first stamps the turn deadline with the repository's clock (`stamp_turn_deadline`, [[GameRules]] § Turn time limit); the repositories take the clock at construction (`with_clock`; `new` is the system clock).
- A human's move that loses answers 409 `GAME_STATE_CONFLICT` ([[Api]]); the client reloads the table on it ([[FlutterGameBoard]]). The bot loop (`run_bot_loop`, `runner.rs`) takes a conflict or a `NotFound` of any of its writes — its moves, its dealing of the next round, its turn hand-over past an eliminated bot — as "read again" (`read_again`), in one place, `BotRunner::settle`: it pauses one `action_delay`, then goes round, re-reads the state and decides afresh (a brain asked again, an LLM bot's a paid request), and ends when no state is left; the retry counts against the loop's action cap. Tests `test_a_lost_race_pauses_before_reading_again` (`runner.rs`) and `test_a_bot_move_that_loses_a_race_pauses_before_asking_its_llm_again` (an LLM bot's play loses to a forfeit; its LLM is asked again only after the pause).

### Auth
- JWT HS256 (`Header::default()`), claims `userId`, `username`, `isAdmin` (default false), `exp`, `iat` (`zapzap-rust/src/infrastructure/auth/jwt_service.rs:7-15`). Lifetime `7 * 24 * 60 * 60` s = 7 days (`:28`).
- Google OAuth (`zapzap-rust/src/infrastructure/services/google_oauth.rs`): `verify_id_token` (`:168`) requires an RS256 token whose `kid` is in Google's JWKS (`https://www.googleapis.com/oauth2/v3/certs`, `:16`), `aud` = `GOOGLE_OAUTH_CLIENT_ID`, `iss` `accounts.google.com` or `https://accounts.google.com`, a valid `exp` (jsonwebtoken default 60 s leeway), and `email_verified` true. Keys are cached 1 h (`:22`). Stale keys or an unknown `kid` trigger a refetch, under one mutex (concurrent requests wait for a single fetch) and at most one attempt a minute, failed or not (`:25`); a failed refetch keeps the stale keys, and its error text is logged, never answered. The JWKS is parsed key by key, skipping keys of an unknown `kty`/`alg` (`parse_jwks`). The client id is trimmed. Tests inject a key set (`GoogleOAuthService::with_keys`) or a fetcher (`with_fetcher`) and never reach the network. A first login that loses a race with a concurrent one answers the winner's user, found again by `google_id`: its save hits the username UNIQUE index when both picked the same name, `idx_users_google_id_unique` (migration 2) when they picked different ones (`racing_first_logins_answer_the_same_user`, `racing_first_logins_on_different_usernames_end_with_one_user`, `login_with_google.rs`). Username of a new Google user: Node's `generateUsername`/`generateUniqueUsername` (`generate_username`, `username_candidate`), which already yields `[a-z0-9_-]`, 3 to 30 characters, so it passes sign-up's rules (unit test `a_generated_username_passes_the_sign_up_rules`); the free-name search is case-insensitive.
- `auth_middleware` requires `Authorization: Bearer <token>` whose user **still exists** in the database (one primary-key lookup, `current_user`, as the Node backend checked; the claims handed on carry the username the database holds, not the token's, which a rename makes stale — `with_current_name`), else 401 with Node's body and code (`MISSING_AUTH_HEADER`, `INVALID_AUTH_FORMAT`, `INVALID_TOKEN`, [[Api]]; `zapzap-rust/src/api/middleware/auth_middleware.rs`, which reads the header with `bearer_token`, shared with the optional middleware). `optional_auth_middleware` attaches claims under the same two conditions (a malformed header or a bad token goes on without claims, as Node's optional middleware). `admin_middleware` is mounted on every `/api/admin` path, unknown ones included (the router's fallbacks are wrapped too), and on `POST /api/bots` / `DELETE /api/bots/:botId`, inside `auth_middleware` (`create_admin_router`, `zapzap-rust/src/api/routes/mod.rs`): it reads `is_admin` **from the database**, as the Node backend did, and answers 401 `AUTH_REQUIRED` / 403 `ADMIN_REQUIRED` with `{success:false, error, code}`. It is the only admin check (the handlers in `admin.rs` no longer read `claims.is_admin`, as in Node): a promotion or a revocation takes effect at once, whatever the token says.
- Party membership: the game use cases check the caller themselves; `nextRound` and `trigger-bot` check it in the handler through `require_party_member` (`zapzap-rust/src/api/access.rs`: 404 `PARTY_NOT_FOUND`, 403 `NOT_IN_PARTY`). Private parties: join needs the invite code, details and history are for members only ([[Api]]).
- Passwords: new hashes are bcrypt at Node's cost 10, `$2b$10$...` (`BCRYPT_COST`, `zapzap-rust/src/infrastructure/auth/password.rs:7-20`), the Node backend's format; `verify` dispatches on prefix `$argon2` vs `$2` (bcrypt: Node's `$2a$`/`$2b$` and Rust's), anything else → `UnknownFormat` (`:38-48`). Login never rewrites the stored hash, and a stored hash `verify` cannot read (unknown format, truncated bcrypt) is logged and answered 401 `INVALID_CREDENTIALS`, as Node's `bcrypt.compare` answers false for it (`zapzap-rust/src/application/auth/login_user.rs`). The cross-check: `zapzap-rust/tests/fixtures/bcrypt_node_compat.json` holds a hash Rust wrote and one bcryptjs wrote, verified by the Rust tests in `password.rs`.

### Account deletion (`DELETE /api/auth/me`)
- `DeleteAccount` (`zapzap-rust/src/application/auth/delete_account.rs`) checks the confirmation with `confirm_identity` (`zapzap-rust/src/application/auth/confirm_identity.rs`, shared with `ChangePassword`) — a password, when one is given and the user has a hash (bcrypt/Argon2 `verify`; an unreadable hash confirms nothing), else a Google ID token whose `sub` is the user's `google_id` and whose `iat` (`GoogleProfile::issued_at`) is at most `GOOGLE_CONFIRMATION_MAX_AGE_SECS` (10 min) old; an account with both (a Google account that set a password) takes either — then calls `UserRepository::delete_account` (`zapzap-rust/src/infrastructure/database/repositories/user_repo.rs`).
- `delete_account` runs in **one transaction**, opened `BEGIN IMMEDIATE` (`pool.begin_with`): it takes SQLite's write lock up front, so a concurrent game or bot write makes it wait out the busy timeout instead of failing with "database is locked" when a deferred transaction upgrades from read to write. User missing → `NotFound`; the only admin → `LastAdmin`; seated in, or owner of, a `waiting` party → `ActiveParty`; then each seat in a `playing` party is forfeited (`forfeit_playing_seats`): with no other human at the table (anonymous `deleted-` users do not count) the party is deleted; else the seat is eliminated in the stored game state (`forfeit_seat`, [[GameRules]]) as a new version (§ Game-state writes), a party the user owned goes to the first other human by seat, and a game left with one active seat is finished there (party and round `finished`, results built and written by `write_game_results` as a ZapZap's are, § Game-state writes; it takes a connection so the transaction can use it). The outcomes come back as `SeatForfeit`s. Then, when any of `USER_REFERENCES` (`parties.owner_id`, `party_players`, `round_scores`, `game_results.winner_user_id`, `player_game_results`, `game_actions`) names the user, it inserts an anonymous human `deleted-<uuid>` (same string as username, no password, no Google id, no email), points those columns at it, and deletes the user row. The foreign keys are on (sqlx's default) and cascade: deleting the row first would take the others' shared games with it.
- The prefix is `DELETED_USER_ID_PREFIX` (`zapzap-rust/src/domain/entities/user.rs`). Ids are server-generated UUIDs, so no account can take it; the leaderboard (`stats.rs`), `find_all_humans` and the admin user list, counts and most active users (`admin.rs`) leave these users out. Nobody can sign in as one (no password, no Google id).
- The handler then drops the user's in-memory session (`SessionManager::remove_user`, which also clears their stream count so their streams close quietly) and broadcasts `userDisconnected`. The token is refused from then on by `auth_middleware`, which checks that the user exists.
- After the deletion, `after_account_deletion` (`zapzap-rust/src/api/routes/auth.rs`, also called by the admin route) forgets the session (`userDisconnected`) and ends the account's streams (`SessionManager::remove_user`), then per forfeit broadcasts `gameUpdate` `playerForfeited` and triggers the bots, or `gameUpdate` `gameFinished`, or `partyUpdate` `partyDeleted`, dropping the party's bot slot in the last two.
- The SQL `LIKE` pattern of the anonymous ids is `deleted_user_id_pattern()` (`user.rs`), always bound, never a literal.
- Tests: `test_delete_own_account_then_its_token_is_refused`, `test_deleted_player_stays_anonymised_in_the_others_history`, `test_delete_account_seated_in_a_waiting_party_is_409`, `test_delete_account_forfeits_the_seat_and_the_game_goes_on`, `test_delete_account_forfeit_leaving_one_player_finishes_the_game`, `test_delete_account_forfeit_leaving_only_bots_deletes_the_party`, `test_delete_account_ends_its_event_streams`, `test_the_only_admin_cannot_delete_their_account`, `test_admin_delete_user_keeps_their_finished_games_anonymised`, `test_admin_delete_user_seated_in_a_live_game_forfeits_the_seat`, `test_admin_party_list_names_a_deleted_owner_anonymously`, `google_and_bot_admin::test_google_account_deletes_itself_with_a_fresh_google_token` (`zapzap-rust/tests/api_tests.rs`); unit tests in `delete_account.rs` (`a_stale_google_token_does_not_confirm_the_deletion` among them) and `session_manager.rs`.
- The admin route `DELETE /api/admin/users/:userId` (`admin.rs`) calls the same `delete_account` after its own refusals (self, an admin target): same anonymisation, 409 for a seat in a live game. It is how an e-mail deletion request is carried out.

### Rename and password change (`PATCH /api/auth/me`, `PUT /api/auth/me/password`)
- `RenameUser` (`zapzap-rust/src/application/auth/rename_user.rs`): sign-up's rules (`validate_username`, `register_user.rs`, shared with `RegisterUser`: trimmed, 3 to 30 characters of `[a-zA-Z0-9_-]`, the rule of `frontend-flutter/lib/utils/validators.dart`; `validate_password`: 6 to 100), its own name accepted as a no-op or a case change, a name taken whatever its case (`UserRepository::exists_by_username_ci`, `LOWER(username) = LOWER(?)`, no unique index: older data may hold case-duplicates, and login still accepts names that break the rules) → `UsernameExists`, a reserved name refused (`is_reserved_username`, `RESERVED_USERNAMES`: `admin`, `Joueur supprimé`, `Deleted player`, trimmed and in any case; also at sign-up) unless it is the account's own in another case, then `UserRepository::update_username` (that column only; a name taken between the check and the write fails on the `username` UNIQUE constraint and answers `UsernameExists` too, unit test `a_name_taken_after_the_check_is_refused_by_the_database`), then a new JWT carrying the name and the `exp` of the token sent (`JwtService::sign_until`), so a rename never extends a session (`test_rename_never_extends_the_session`). The name lives only in `users`: every other table joins on the id, so history and statistics follow. The handler renames the connected session (`SessionManager::rename_user`).
- Tokens issued before a rename keep the old name until they expire: `auth_middleware` hands the handlers the database's name instead (§ Auth), and `sse_handler` registers the stream under it, so a `playerJoined` or `userConnected` sent with an old token names the player as they are now (`test_rename_answers_a_token_carrying_the_new_name`).
- `ChangePassword` (`zapzap-rust/src/application/auth/change_password.rs`): sign-up's rule for the new one (`validate_password`), then `confirm_identity` (§ Account deletion) with `currentPassword` or `credential`, then `update_password_hash`. A Google account without a password sets its first one this way, and then also signs in with its username (`/login`). Tokens already issued stay valid: the JWT carries no password. Tests: `test_change_password_needs_the_current_one`, `google_and_bot_admin::test_google_account_sets_a_first_password_with_a_fresh_google_token`; unit tests in `confirm_identity.rs`.

### Guest accounts (`POST /api/auth/guest`)
- `CreateGuest` (`zapzap-rust/src/application/auth/create_guest.rs`): a password of `GUEST_PASSWORD_LENGTH` (24) letters and digits from `rand::rng()` (ChaCha12 seeded from the OS), hashed as registration hashes; then up to 20 names `Guest_` + 8 digits (14 characters, 10⁸ names) (`guest_username`), each checked with `exists_by_username_ci` and saved as `User::new_guest` (`is_guest` true); a save that hits the `username` UNIQUE constraint draws again. No free name → `NoFreeName`, 500. Unit tests `a_name_taken_in_any_case_or_after_the_check_is_drawn_again`, `no_free_name_is_an_error`, `a_guest_name_passes_the_sign_up_rules`.
- The handler (`guest_handler`, `auth.rs`) takes the client address (`client_ip`) first and asks `state.guest_limiter` (`RateLimiter`, `zapzap-rust/src/infrastructure/rate_limit.rs`); refused → 429 `RATE_LIMITED`, logged at warn. A creation that fails (500 `GUEST_ERROR`) gives its slot back (`RateLimiter::release`): it created nothing (`test_a_failed_guest_creation_does_not_count_against_the_client`). A creation logs at info the name, id, derived address and number of `X-Forwarded-For` entries — never the password. The address rule and why it is trusted: [[Api]] § Guest accounts.
- **The claim**: `UserRepository::update_password_hash` also sets `is_guest = 0`, so the first password a guest chooses (`ChangePassword`, which answers the updated user) makes it a full account. `reset-password` goes through `save` and keeps the flag: a password an admin sets is not the player's choice.
- Nothing purges abandoned guests (open question, user decision 2026-09-29).

### Turn timer
- The rule, the setting, the clock in the game state and how the deadline is stamped: [[GameRules]] § Turn time limit. This section is the task that enforces it (`zapzap-rust/src/application/game/turn_timer.rs`).
- `spawn_turn_timer(state, every)` runs `enforce_turn_deadlines` every `TURN_TIMER_TICK` (1 s; missed ticks skipped) for the server's lifetime; it keeps nothing in memory, everything is read from the database, so a restart loses no deadline. The deadlines are absolute Unix ms, so before its first tick it runs `extend_turn_deadlines_after_downtime` once: every turn under way whose deadline is before start + its limit gets start + its limit (compare-and-swap; the same turn keeps it), so a deploy's downtime ejects nobody. `enforce_turn_deadlines` reads `state.clock`, asks `parties_past_turn_deadline(now)` (`party_repo.rs`: the playing parties whose `json_extract(state_json, '$.turnDeadline') <= now`), and runs `EjectLatePlayer` on each.
- `EjectLatePlayer::execute(party_id, now)` re-reads the versioned state and does nothing unless `late_seat(now)` names a seat held by a human. The stand-in is a bot not seated at the table, `medium` first, then `hard`, the other rule-based bots, an LLM bot last, by username; with none free it makes `StandInBot-<8 hex>` (`medium`), which `replace_player` inserts inside its transaction (`SeatReplacement::new_bot`), so an ejection that loses its race leaves no bot behind. The party passes to the first other human by seat (anonymous `deleted-` users skipped) when the late human owned it; with no other human, to the stand-in on the late human's seat, so the owner is always a player of the party while the bots play it out. `replace_player` (`party_repo.rs`) writes it all in one `BEGIN IMMEDIATE` transaction: the game state through the compare-and-swap (the seat untimed), `party_players.user_id` of the seat (only if still the human's), the owner, and the human's `player_game_results` loss, the earlier ejected moved down one, all ranked by `rank_ejected` ([[GameRules]] § Final ranking). A move that wrote first makes it a `Conflict`: nothing is written, the ejection does not happen, and the next tick looks again.
- After an ejection: `gameUpdate` `playerReplaced` `{playerIndex, replacedUserId, replacedUsername, botId, botUsername, newOwnerId}`, sent in the ejected human's name (`userId`) so their own stream hears it too (§ Event broadcaster / SSE, "own action"), and the bots are triggered (300 ms). The ejected human is no longer in `party_players`: every game route answers them 403 `NOT_IN_PARTY`; their history and stats keep the game through their `player_game_results` row.
- Tests (`zapzap-rust/tests/turn_timer_tests.rs`, `ManualClock`, no waiting): `test_a_late_human_is_replaced_by_a_bot_and_the_game_plays_to_its_end` (2 humans, 30 s: nothing at 29 s, ejection at 30 s, both streams get `playerReplaced`, the party passes on, the other human and the bots play to the end), `test_an_ejected_human_can_no_longer_play` (403 `NOT_IN_PARTY` on the state and every move while the game goes on), `test_an_ejected_humans_game_is_a_loss_whatever_the_bot_does` (`/stats/me` a loss at once and after the end, the stand-in winning with the seat), `test_a_party_started_with_one_human_runs_no_clock`, `test_the_turn_deadline_is_in_the_state_and_restarts_only_with_the_next_turn`, `test_the_clock_covers_the_whole_turn_hand_size_choice_included`, `test_a_move_read_before_an_ejection_is_refused`, `test_a_move_whose_seat_is_given_away_after_its_seat_check_is_refused` (a repository wrapper runs the ejection between the move's seat check and its state read), `test_an_ejection_that_loses_the_race_to_a_move_writes_nothing` (no stand-in created either), `test_the_turn_timer_task_ejects_on_its_own` (started after a downtime), `test_a_restart_does_not_count_the_downtime_against_the_player_on_turn`, `test_the_last_human_ejected_hands_the_party_to_the_bot_on_their_seat`, `test_create_party_offers_off_30_60_and_120_seconds_per_turn`, `test_two_players_ejected_in_turn_rank_4th_and_5th_of_5`, `test_an_ejected_player_ranks_after_every_seat_when_a_forfeit_ends_the_game`, `test_rewritten_game_results_count_the_ejected_players` (the ranking of the ejected, [[GameRules]] § Final ranking).

### Event broadcaster / SSE
- `broadcast(1000)` with `set_overflow(true)`: when full, oldest events are dropped instead of blocking (`app_state.rs:114-115`). `broadcast_event` uses `try_broadcast` and only logs errors (`:208-226`).
- `GameEvent` JSON: `type`, `partyId`, `userId`, optional `action`, flattened `data`, `timestamp` ms (`app_state.rs:230-244`). Event types emitted: `partyUpdate` (actions `partyCreated`, `playerJoined` — also when the owner adds a bot, with the bot as `userId` —, `playerLeft`, `partyStarted`, `partyDeleted` — with the `visibility` the deleted party had), `gameUpdate` (`selectHandSize`, `play`, `draw`, `zapzap`, `roundStarted`, `gameFinished` — sent by `nextRound` and the bots' deal, which the zapzap ending a game makes unreachable: that zapzap sends `zapzap` only, so no `gameFinished` goes out in normal play (a forfeit's excepted, § Account deletion) —, `playerForfeited` — a seat given up by a deleted account, `{playerIndex}` —, `playerReplaced` — a late human's seat taken by a bot, § Turn timer), `userConnected`, `userDisconnected`.
- `GET /suscribeupdate?token=<jwt>` (`zapzap-rust/src/api/sse.rs`): token optional, passed in the query string. Sends an initial `connected` event, then each GameEvent as SSE event `event`, a `heartbeat` comment every 20 s, plus axum's default keep-alive comment; response header `X-Accel-Buffering: no` (and axum's `Cache-Control: no-cache`) so no proxy buffers the stream.
- **Per-user filtering** (`should_deliver`, `sse.rs`): an event without `partyId` (`userConnected`, `userDisconnected`, `userStatusChanged`) goes to every stream, as Node sends everything to everyone; so does a **public** party's lifecycle event (`PUBLIC_LIFECYCLE_ACTIONS`: `partyCreated` (emitted for public parties only), `playerJoined`, `playerLeft`, `partyStarted`, `partyDeleted`, `gameFinished` — names, indexes and ids only), which the Flutter `PartyListProvider` reloads the party list on; a `partyDeleted` carries the `visibility` the deleted party had. Every other party event — `gameUpdate` moves, and every event of a **private** party — goes only to a stream whose token names a player of that party (checked in `party_players` per event), or whose own action it reports (the player who just left), and a `partyDeleted` also to the streams that were players of it when they opened or since (its membership rows are gone by then). If the membership lookup fails, the stream goes by the parties it already knew and changes nothing. A token whose user no longer exists names nobody. A stream without a valid token gets the events that go to everyone only. The Node backend filtered nothing.
- On a receiver error (e.g. lagging) the stream breaks and the client must reconnect.
- An authenticated stream owns a `StreamGuard` (`sse.rs`): when the client goes away axum drops the stream, and the guard's `Drop` unregisters it from the session manager; the user's last stream broadcasts `userDisconnected` (with the session's `username`, which a rename while connected has updated), their first one `userConnected` (with the database's name, not the token's), as the Node backend did. Tests: `test_sse_disconnect_unlists_the_user_after_the_last_stream` (`zapzap-rust/tests/api_tests.rs`).

### Session manager
- In-memory, lost on restart (`zapzap-rust/src/infrastructure/services/session_manager.rs`): the sessions by user id, and the number of open event streams per user, as Node's `SessionManager.streams`. `connect` registers a stream and returns the new session (status `lobby`) only on the user's first one; `disconnect` unregisters one and returns the removed session only on the last one. `connect` also hands the stream the user's close signal (a `tokio::sync::watch`), taken under the same lock; `remove_user` (an account deleted) fires it and the streams end. `sse_handler` checks that the account exists only after `connect`: a deletion before the check is seen by it (the stream is unregistered quietly and goes on anonymous), one after it fires the signal (test `a_removal_right_after_connecting_reaches_the_new_stream`). Two tabs, or a reconnection whose new stream opens before the old one closes, keep the user listed with their session as it was.
- `update_status` is never called, so every session stays `lobby` with `partyId: null`. `rename_user` changes a connected user's name (`PATCH /api/auth/me`, or a stream opened with a token issued before a rename).
- `GET /api/players/connected` returns at most 5 sessions, newest first (`zapzap-rust/src/api/routes/players.rs:39`).

### Bot triggering
- No bot scheduler: bots move when a request triggers them. `GET state` (100 ms delay), `selectHandSize`, `play`, `draw` and `nextRound` (300 ms) call `spawn_bot_turns` (`zapzap-rust/src/application/bot/runner.rs`), which runs `trigger_bot_turns` in a `tokio::spawn`. The loop plays while the current player is a bot, and deals the next round once no human is left in the game ([[Bots]]), pausing after each action for `BOT_ACTION_DELAY_MS` (`BotRunner::action_delay`, 1000 ms by default as Node; the tests run at 200 ms; `test_bot_actions_pause_for_bot_action_delay_ms`).
- **One loop at a time per party**: `AppState.bot_runner` (`BotRunner`) keeps one slot per party — a `pending` flag and the party's `Roster` behind a tokio mutex. A trigger sets `pending` and returns at once when a loop holds the mutex; the running loop goes round again while `pending` is set, and re-checks it after unlocking, so no trigger is lost and no two loops act on the same party. The slot is dropped when the party is no longer playing, and at once when the party is deleted (`BotRunner::drop_party`, from `DELETE /api/party/:id` and the admin delete); a loop that runs meanwhile finds no game state at its next action and ends.
- **One strategy per bot for the game**: the `Roster` builds a bot's `BotBrain` (a rule-based `BotStrategy`, or the `LlmBotStrategy`) on its first move and hands back the same instance afterwards; hand size is the strategy's choice, clamped by `hand_size_bounds` (`game_service.rs`: 4-7, 4-10 in Golden Score, at most (54 − 1) / active players). See [[Bots]].
- Action cap per loop and per round: 50 if an active human remains, 500 if only bots (`MAX_ACTIONS_WITH_HUMANS`, `MAX_ACTIONS_BOTS_ONLY`); the count starts again with each round the bots deal once no human is left in the game ([[Bots]] § How bot turns are triggered).
- A bot move that loses a race with another write of the game state is read again and replayed, not an error (§ Game-state writes).
- Manual `POST /api/game/:partyId/trigger-bot` (`game.rs`) calls `run_bot_turns_now`, which waits for the party's running loop, then runs one itself and answers the number of actions taken (500 `BOT_ACTION_ERROR` on a failed bot action). A trigger that came meanwhile is served afterwards in the background (`serve_pending`; test `test_trigger_during_a_manual_loop_is_served_after_it`).
- After a ZapZap (a human's, from `game.rs`, or a bot's, from the loop), `trigger_llm_reflection` (`runner.rs`) runs `ReflectOnRound` for each LLM bot if an LLM service exists, with the round outcome `round_outcome` reads from the round-end state: `score_change` is the points the round added to the bot's total (`round_scores`).
- Pending bot turns are not recovered at startup (the Node backend's `recoverPendingBotTurns` has no Rust equivalent); the next `GET state` restarts them.

### Error mapping
- The party and game handlers return `Result<_, ApiError>` (`zapzap-rust/src/api/error.rs`): one `From<UseCaseError> for ApiError` per use case maps each variant to Node's status and `code`; no handler reads an error's message. A repository failure is a 500 in Node's shape (`{error: "Failed to …", code: "<ROUTE>_ERROR", details}`), logged by `IntoResponse`. But a move's `RepositoryError::Conflict` is 409 `GAME_STATE_CONFLICT`, and its `NotFound` (the game state gone meanwhile) 404 `PARTY_NOT_FOUND` (`game_write_failed`).
- JSON bodies go through `ApiJson<T>`: a body that does not parse (malformed JSON, a missing or mistyped field) answers 400 `{error, code}` (Node's body: no parser message in `details`) with the code the route gives a missing field (`ApiBody::INVALID_CODE`), never axum's 422 plain text; a request without a JSON content type reads as `{}`, as Express does.
- The auth, admin, bots, stats and history handlers still build their errors inline (no message matching there).

## Decisions & History
- 2026-09-29 (fix/e2e-deterministic-round): the Flutter end-to-end round still ran past its move budget at random (#162: 30 turns, a hand of 2 points after each play and a high card drawn). No driver strategy bounds a random round: four high cards of four ranks and high draws keep a hand over 5 points for good. Chosen: a fixed deal, cards in id order, behind `ZAPZAP_TEST_FIXED_DECK=1` and compiled into debug builds only, so the production image cannot honour it whatever its environment. Rejected: a seed (a deal that changes with the `rand` version, and a seed to search for), and an explicit card list in the variable (a parser in production code for one test). Only the deal at hand-size selection is fixed: `initialize_round`'s is thrown away, and the reshuffle is not reached in two turns.
- 2026-09-29 (fix/bot-loop-lost-race-backoff): a bot write that lost a race went round at once, so the loop re-read the state and asked its brain again with no pause; for an LLM bot each retry is a paid request, and under sustained contention the loop could spin to its cap (50 or 500) in a tight loop. It now pauses one `action_delay` first, the delay the loop already waits after a move. Chosen over a separate fixed backoff: one setting, and a lost race means another write just landed (a forfeit, a human's move, a round dealt), which the clients get the same pause to show; rejected, a floor under a `0` delay, which only the tests and the end-to-end run set. The six places that each matched their use case's `Repository` error against `read_again` became one, `BotRunner::settle`, over a small `BotWriteError` trait the use-case errors and `RepositoryError` implement; the dealing of the next round and the hand-over past an eliminated bot go through it too, so every bot write settles a lost race the same way.
- 2026-09-29 (feat/guest-play): guest accounts. `is_guest` is a column (migration 3) rather than a name prefix, because a guest may rename itself and still be one, and a player could register a `Guest_` name. The claim clears it in `update_password_hash` itself rather than in a second statement of `ChangePassword`, so the two cannot disagree. The client address is read from `X-Forwarded-For` counted from the right, a fixed number of trusted hops, because the leftmost entry is whatever the client sent; the hop count is a setting (`TRUSTED_PROXY_HOPS`) with production's topology as its default, and the creation log line is how it gets checked after a deploy. `main.rs` serves with `into_make_service_with_connect_info` so a backend with no proxy in front still tells clients apart.
- 2026-09-29 (feat/account-page): a player renames the account and changes or sets its password. Dedicated `update_username` / `update_password_hash` rather than `save`, whose upsert of the whole row read before would undo a concurrent change of another column (an admin flag). The confirmation of a deletion became `confirm_identity`, shared with the password change, and now takes **either** proof from an account that has both: before, a password hash made the password the only proof, so a Google account that set a password could no longer be deleted with the Google button the Flutter dialog shows it. The middleware reading the name from the database instead of the token costs nothing (it already loads the row) and spares a 7-day window where the player's other devices announce the old name. After review: reserved names (`admin` was protected by the admin screens by its name only), the rename token's `exp` kept, and `/login` answering `/google`'s user shape (`AccountUserInfo`).
- 2026-09-28 (fix/game-write-atomicity): the game use cases wrote the state through the compare-and-swap, then the round row, the round scores, the party row and the results in separate statements on the pool. A forfeit that passed the party on between `nextRound`'s read of the party and its write was undone by the whole-row `party.save` (a foreign-key 500 once the old owner was deleted, the state already at round N + 1); a failed round-row write left the state at N + 1 without its row; an admin stop, which wrote only `parties.status`, let a move read before it through; the game's end read the ejected players on one connection and wrote the results on another, so an account deletion in between failed it with a 500 after the party was finished. Chosen: one repository call per use case, `write_game(GameWrite)`, a description of the writes run in one `BEGIN IMMEDIATE` transaction opened by the compare-and-swap, the results read and built inside it (`write_game_results`). Rejected: a transaction handle given to the application layer (sqlx types in the domain trait, and the test wrappers over `PartyRepository` would need a transaction abstraction of their own); writing only the changed party fields but keeping separate statements (it fixes the owner, not the half-written round). The admin stop both bumps the version and is checked by status in the compare-and-swap: the version alone misses a stop between a move's party read and its state read. A state gone is `NotFound` (404) rather than a conflict the client would reload into a 404 anyway. The round rows are found by the state's round number rather than `parties.current_round_id`, read before the transaction.
- 2026-09-28 (feat/turn-timer-backend): the turn timer is one background task polling the database every second rather than a tokio timer per deadline: it needs no bookkeeping when a move beats the deadline, and a restart loses nothing (per-party timers would have had to be rebuilt at startup, as the bot turns are not). The deadline is stamped by the repositories' writes rather than by each use case, with a `Clock` shared through `AppState` so that tests move time by hand; the ejection is one transaction whose game-state write is the moves' compare-and-swap, so a move that lands first wins and a move read before the ejection is refused. Why the rule and its choices: [[GameRules]] History.
- 2026-09-27 (fix/google-id-unique-index): `users.google_id` got a partial unique index (migration 2), because Node's plain index let two first logins of one Google account racing on different usernames create two users, and `find_by_google_id` then answered either. Partial (`WHERE google_id IS NOT NULL`) because password users and bots all hold NULL. Production was checked read-only for duplicates first (none: 2 users with a Google id, 2 distinct ids). Node's plain `idx_users_google_id` is kept rather than dropped: `schema.sql` recreates it anyway (`IF NOT EXISTS`), and keeping the steps additive keeps a rollback safe. `create_user` needed no change: it already treats any UNIQUE violation by re-reading the account.
- 2026-09-27 (feat/reset-password-subcommand): a `reset-password` subcommand replaces the Node
  backend's `reset-password.js` script (removed with it, readable at `232f168`), which hard-coded one
  username/password pair. A subcommand beside `seed` rather than an admin route: the image
  already ships it, it needs no `JWT_SECRET` or running server, and it shares

- 2026-09-27 (fix/game-state-version): the game-state writes were unsynchronised read-modify-writes, so a write based on a stale read undid the one before it: a move that read before an account deletion's forfeit and wrote after it brought the forfeited seat back as active, and the game waited on a player who no longer existed; two `nextRound` at once answered 500. Chosen: an integer `version` with compare-and-swap (optimistic locking), rather than one async mutex per party in `AppState` (the forfeit runs in a repository transaction a mutex cannot reach, and a lock covers only this process), a compare on `updated_at` (seconds: two writes in one second compare equal) or on the JSON (the whole state in every `WHERE`). A human's lost move is a 409, not replayed server-side: the player chose it on a table that has changed. The bot loop replays, since it decides afresh from what it reads. The column came with the first migration; migrations are counted in `PRAGMA user_version` rather than detected per step (a column check for each) or run by `sqlx::migrate!` (a bookkeeping table on the production file, see 2026-09-23).
- 2026-09-27 (fix/account-deletion-followups): an account deletion forfeits the user's seats in games in progress, in the deletion's transaction, rather than refusing with 409: a game the others abandoned blocked the deletion for ever (see [[Api]]). The forfeit is written with SQL in `user_repo.rs` rather than through `PartyRepository`, whose methods run on the pool and cannot join the transaction; a check that fails after it (none does today) would roll it back with the rest. It shares the pool-free pieces instead (`forfeit_seat`, `sort_final_ranking`, `elimination_order`, `write_game_results`).
